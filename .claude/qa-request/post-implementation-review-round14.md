**Q184 [2026-10-07 §6, 정의 범위 — 처리 도중 돌아온 엔진 왕복이 같은 자리에 다른 값을 넣는 것]** 상황: core/05는 `q.Out`·`OnChange` 엔진 왕복을 정상(정의된 예외)이라 하고 그 근거를 "엔진은 같은 값이면 신호를 안 내고 `q.Out`은 같은 값을 거르므로 한 바퀴에서 멈춘다"로 적는다. 한편 core/07 66과 `dispatch-core-plan.md`(Q5 (a), Q162 재확인)는 "어느 핸들러든 같은 자리를 처리하는 도중 같은 자리로 다른 값을 넣는 재진입은 UB"다. **Q185 [2026-10-07 §6, 동작 결함 — Immediate에서 원소의 `Parent` 신호가 같은 Slot을 CRUD하면 부기가 깨진다]** 상황: Slot 원소에 `q.OnChange("Parent", fn)`을 달고(`Parent`는 읽기 표면 — Q35) `fn`이 같은 Slot을 `Add`/`Remove`하는 것은 같은 `(inst, k)` 재진입이 아니라 core/07 UB 밖이고, `slot-plan.md` 재진입성 절도 막지 않는 평범한 경로다. 그런데 Immediate에서 그 신호가 native op 안에서 동기로 오면 `mountSlotTree`·`rawSplice`·`unmountSlotTree`·`rawRemove`/`rawUnmount`/`rawDetach`가 native op 전에 잡아 둔 위치·표시로 꼬리를 마저 처리해, 원소가 부기엔 있는데 화면에 없거나(SL3·SL8), 옛 호스트에 남거나(SL5), **다른 원소를 빼내는**(SL6 — 조용함) 결과가 난다. Deferred에선 전부 정상. Roblox `Destroy`가 Immediate에서 `Parent` 변경을 동기로 내는지는 미실측(mock 순서 기준). 갈래: (a) 후보 S4의 Slot 부분 반영 — 기록을 native op 앞으로 옮기고 vacate 전에 `indexOfElement`로 index를 다시 찾는다(새 필드·이름 없음, spec 62/62, imm = def) + spec 절 / (b) 이 경로를 UB로 문서화(원소의 엔진 신호 콜백에서 그 Slot을 CRUD하는 것) / (c) 실기기(Destroy·Parent 신호 동기성) 뒤 결정. 메인 권고 (a) — 비용은 재정렬과 역맵 조회 한 번이고, 특히 SL6은 Deferred가 기본이어도 Immediate 경험에서 조용히 다른 원소를 잃는 결함이라 문서 UB로 덮기엔 결과가 나쁘다; 실기기는 우선순위만 바꾼다.
