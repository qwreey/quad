## §4 사용자 문항 (평문 — 내일 검토)

**Q48 — 정적 자식 자리에는 요소 소유권 부기가 없다(HIGH, 탐사 C F1, 실행 재현).** 상황: `Handlers/InstanceChild.luau`는 오늘 넣은 `isClaimed` 게이트만 보고 `elementOwner` 부기(어느 자리가 이 요소를 쥐는가)는 만들지 않습니다. 그래서 `local c = D.TextLabel{}`를 `D.Frame({c})`에 넣고 다시 다른 `D.Frame({c})`에 넣으면 에러 없이 둘째가 가져가고 첫째 부기엔 length 1이 남으며, 첫째가 자기 자리를 철거하면 retractor의 `v.Parent = nil`이 **살아 있는 둘째 트리에서 c를 뜯어냅니다**. `D.Frame({c, c})`도 통과(물리 1, 부기 2), 정적 자리의 값을 `slot:Add`가 가져가고 반대도 되며, `q.dispose(c)`가 정적 자리의 값을 막지 않고 파괴하고(그 거부 메시지는 "mounted position"을 포함해 말함), `Claim`이 props를 제자리에서 바꾸므로 같은 props 테이블을 두 `Claim`에 쓰면 첫 트리의 자식이 둘째로 끌려갑니다. 무엇이 막히나: `slot-plan.md` "핵심 제약: 소유권 귀속과 단일 마운트"가 *"한 인스턴스에 대한 다중 마운팅이 라이브러리 차원에서 절대 일어나지 않도록 강제"*라 못 박았는데 Slot만 그 불변식 안에 있고 정적 자리는 밖입니다 — 오늘 `claim-plan.md` 14번이 "Slot 게이트와 대칭"으로 넣은 것은 `isClaimed` 축뿐입니다. 갈래: (a) `InstanceChild`가 Slot과 같은 `elementOwner` 레지스트리에 `(inst, k)` 자리로 등록·해제해 이중 마운트를 거부하고 `dispose`도 막는다 — 그 레지스트리 op(`claimOwnerAt`/`releaseOwner`)는 quad-base `Slot/Owner.luau` 내부라 **quad-roblox가 부를 공개 경로가 없어 `q.Bookkeeping`(또는 새 네임스페이스)에 소유권 op를 노출**해야 합니다(새 표면, 프로바이더 계약 확장 — BREAKING 주간 안) / (b) 정적 자리를 공인 adoption 경로로 두고 문서에 "정적 자리는 소유 검사가 없고 두 번 놓으면 마지막이 이긴다"를 명시(코드 0) / (c) 그대로. 메인 권고 (a) — 오늘 대칭 게이트 결정의 논거(조용한 stale 금지)가 그대로 적용되고, 사용자가 `Offset`을 `LayoutOrder`로 쓰는 관용구가 조용히 어긋나는 것이 실제 피해입니다. 재현 `scratchpad/hunt-c/tmp-hunt-c-12-ignoreme.luau` §D.

**Q49 — `Claim`이 매퍼 디스크립터의 클래스와 실제 자식의 ClassName을 대조하지 않는다(MED, 탐사 C F4).** 상황: `M.TextLabel("Kid")`가 실제로는 `ImageLabel`인 자식을 잡아도 props가 공통 이름뿐이면 에러 없이 통과하고 사용자는 `TextLabel` 타입의 핸들을 받습니다; props가 안 겹치면 `Dispatch: no handler matched key Text`가 나는데 그땐 이미 루트·자식이 claim되고 디스크립터가 소진돼 트리가 반쯤 적용된 채 남습니다. 무엇이 막히나: quad-base의 `Claim`은 ClassName을 모릅니다(백엔드 개념). 갈래: (a) `nativeFindChild(inst, key)`의 결과를 백엔드가 클래스로 검증하도록 **op 시그니처에 클래스 이름을 더한다**(`nativeFindChild(inst, key, className?)` — 계약 변경) / (b) quad-roblox의 `newMapperClass` 쪽에서 디스크립터에 검증 훅을 심어 base가 resolve 뒤 부른다(새 디스크립터 필드) / (c) UB로 문서화만. 권고 (a) 또는 (b) 중 base가 클래스 개념을 안 갖는 (b)에 가깝습니다 — 어느 쪽이든 새 메커니즘이라 문항.

**Q50 — `State._recompute`에 재진입 가드가 없고 의존성 순환에 진단이 없다(탐사 B F2·F4).** 상황: Observer/Effect는 `_running`으로 자기 재진입을 막지만 `_recompute`만 무가드라, Compute fn이 yield하는 사이 다른 코루틴이 `:Get()`하면 fn이 처음부터 다시 돌아 부작용이 세대당 두 번 나고 늦게 재개된 쪽이 캐시를 덮습니다(`state-epoch-plan.md` §4 `H-85`가 yield하는 Compute를 상정만 하고 이 경우는 안 다룸). 같은 자리에서 `a:Compute(fn)`의 fn이 자기/하류를 읽는 **순환**은 `EpochMap.luau:104: stack overflow`로 내부 파일을 blame하고, 그 오버플로를 `q.Fallback` 같은 프레임이 삼키면 반쯤 계산된 값이 **유효 캐시로 굳습니다**(실측). 갈래: (a) `_recompute`에 `_computing` 플래그를 두고 재진입이면 `State: dependency cycle or re-entrant Compute (…)`로 던진다 — 순환은 사용자 줄 blame으로 잡히고, yield 중 재진입도 시끄럽게 실패(= "Compute는 yield하지 않는다"를 규칙으로) / (b) 순환만 진단하고 yield 재진입은 허용해 fn을 다시 돌리되 문서화 / (c) 둘 다 UB로 문서화만. 권고 (a) — 이 코퍼스의 fail-fast 원칙과 맞고 `H-500`(Slot 순환 가드) 선례가 있습니다. 재현 `scratchpad/hunt-b/tmp-hunt-b-12-ignoreme.luau` A, `tmp-hunt-b-10-ignoreme.luau` C.

**Q51 — Effect cleanup 안에서 dep을 `Set`하면 (cleanup+fn) 사이클이 같은 입력으로 한 번 더 돈다(탐사 B F3).** 상황: `rawRerun`은 `_pending = false` → cleanup → fn 순서라, cleanup이 `a:Set(99)`하면 그 요청이 `_pending`에 남아 뒤따르는 fn이 이미 99를 읽었는데도 루프가 한 바퀴 더 돕니다(로그 `cl fn cl fn`). `effect-plan.md` 의사코드도 같은 순서라 코드 결함이 아니라 플랜이 안 따져본 경계입니다. 갈래: (a) `_pending`을 fn 직전에 내린다(cleanup 중 요청은 뒤의 fn이 소비) / (b) 그대로 두고 "cleanup에서 dep을 쓰지 말 것"을 문서화. 권고 (a) — 이벤트 연결/해제 cleanup에서 불필요한 왕복이 실제 비용입니다.

**Q52 — 중첩 `:List`의 첫 마운트 `updateFn`이 바깥 Slot을 CRUD하면 마운트 walk가 깨진다(탐사 A 2).** 상황: `materializeSlotTree`가 `ipairs(_elements)`를 돌며 그 안에서 중첩 `:List`의 `updateFn`을 부르는데, 그 콜백이 바깥에 `Add(extra, 1)`을 하면 `bindLifetime: value is already bound`로 drive가 죽고 부기가 영구히 깨집니다(같은 뮤테이션을 Observer 안(마운트 walk 밖)에서 하면 정상). `slot-plan.md` "재진입성" 절이 *"별도 가드 불필요"*라고 적어 둔 경로라 문서와 어긋납니다. 갈래: (a) 마운트 walk 중 조상 Slot CRUD를 감지해 `Slot: cannot mutate an ancestor Slot while it is being mounted`로 던진다(새 가드 — 표면은 아님) / (b) walk를 스냅샷 위에서 돌게 고쳐 지원 / (c) 재진입성 절에 "마운트 walk 안은 예외(UB)"로 좁힌다. 권고 (a).
