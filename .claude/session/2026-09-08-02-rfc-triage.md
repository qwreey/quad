# 2026-09-08-02 — 사용자 반입 RFC 다섯(무시 파일) 판정·실측·반영 (오전, 대화형)

## 1. 입력과 지시

사용자가 값싼 모델을 여러 번 돌려 시각을 합쳐 둔 무시 파일 다섯을 지목했다 — 코드 품질 하나
(code-quality-and-doc-structure)와 성능 넷(slot-list-seen-swap / slot-list-reorder-technical-analysis /
rfc-minor-optimizations / bookkeeping-abs-ondemand). *"저 의견들이 사실인지, 문제가 없는지, 더 나아갈 수 있는지,
여럿 고려해서 읽어봐야해 … opus/sonnet 모델을 굴려도 좋으니, 판단해보고 타당한 적용 가능한게 있는지, 더 확장해
나아갈 수 있을지, 내 결정이 더 필요할지 보며 작업을 진행해보자"*. 그 밖의 무시 파일(comparison-vide-fusion,
unexplored-perspectives-and-roadmap)은 *"아직 작업중인것들이 대다수"* — 손대지 않았다.

메인이 서브에이전트 없이 직접 했다 — 판정의 실질이 코드 대조 + 실측이고(conventions "문서 추론형 작업은 쪼개지
않는다"), 대상 소스가 Bookkeeping·Slot/List·Slot/Raw·Slot/init·Modifier·Dispatch 여섯 파일이라 직접 읽는 게 쌌다.

## 2. 방법 — 주장마다 코드 대조, 성능 주장은 실측

`quad-base/test/probe.tmp.luau`(mock CLI)로 변경 전후를 쟀다(표는 원장 §1). 핵심 셋: `Clear`/`ExtractAll`

List 역순 1000개 82ms(RFC 추정 19.6ms보다 큼), 100개는 1ms; flat `recompute` 0.42ms 중 `getOffsetAt` 채우기 0.18ms.
getHandler 분담은 quad-roblox 핸들러 22개를 실제로 설치해(`spec.handlers`의 부트스트랩 관용구) 문자열 프로퍼티
10개짜리 `D.Frame`에서 `isHandlable` 150회, 46.5µs 중 9.2µs.

## 3. 결정 흐름

- **abs 온디맨드**: 메인은 처음 기각 쪽으로 정리했다 — 이득 상한 0.18ms/1000자리, 캐시 채움은 숫자를 뽑는 곳이
  어차피 다시 하므로 이동이지 제거가 아니고, `spec.lengthoffset` 6절이 "recompute가 캐시를 재구축"을 단언. 사용자가
  중간에 끊었다: *"abs 온디맨드는 큰 부작용이 없고, 바로 적용 가능하고 20줄 이내 패치라 기각할 이유는 없어보이는데?"*
  → 정확성 재확인(None 자리엔 진입 스냅샷 뒤 사용자 코드 창이 없어 검사 ① 생략이 안전) 뒤 적용(`H-483`), 6절
  단언은 "당겨진 채 남고 값 읽기가 채운다"로. 실측 0.42 → 0.11ms.
- **ExtractAll → `self:Splice(1, n)` 위임**(RFC 처방)은 쓰지 않았다 — 태그된 공개 메소드가 태그된 공개 메소드를
  부르면 안쪽 raise의 blame이 위임 줄로 가는 `H-385` 규약. `S.rawSplice(self, 1, n, {})` 직접 호출 + 언랩.
- **IndexOf의 `self._elements[idx] == element` 재확인**(RFC)은 안 넣었다 — `settle`이 같은 역맵을 무검증으로
  쓴다; 어긋나면 raw* 층의 버그. "드문 오용 방어에 구조를 쓰지 않는다".
- **seen 스왑의 재진입 논거**: 옛 clone도 재진입은 막지 못했다(순회 중 변형만) — 그리고 Lua/Luau `pairs`는 순회
  중 기존 키 nil 대입을 허용하므로 clone은 애초에 불필요했다. 스왑은 그 위에 N번의 해시 쓰기까지 없앤다.
- **재정렬 분석 문서의 난제 2·5는 현재 코드에 없다** — `rawMove`가 `bk.observers`를 같은 순열로 돌리고
  `releaseElement`는 역맵으로 인덱스를 얻는다. 그 문서가 제안한 "덮어쓰기" 중간 상태의 문제다. 병목 자체와
  원인 서술은 맞다. 처방(`rawPermute`)은 새 raw op라 문항(Q38).
- **getHandler 버킷**은 사용자가 방향을 승인한 항목이지만 핸들러 계약 필드가 필요해 이름·모양을 문항으로(Q37).
  RFC 예시의 "전체 폴백 순회" 주석은 코드가 없는 빈말 — 버킷은 "선언 ∪ 미선언"이어야 서드파티가 안 빠진다.
- **코드 품질 문서**: 2.1 일괄 태깅 기각(`H-434`의 함정 전면화, 각 Init이 자기 표면을 태그, round6 기각 3),
  2.2·2.3·2.4는 기존 문서가 이미 소스(architecture "코드 스타일 — 네이밍 케이싱" / lifecycle-pattern (0.5)·
  relate-plan `H-71`·dispatch-core-plan `H-229` / typing-limits 8.11), §3 거버넌스 넷은 문항(Q39). 그 문서가
  인용한 규약 *"파일당 200줄 권장"*은 코퍼스에 없다(grep 0건) — 수치는 맞다.

## 5. 교훈

- 실측이 문서의 추정을 두 방향으로 다 뒤집었다: Clear/ExtractAll은 RFC가 "GC churn" 정도로 적었는데 O(N²)였고,
  abs 온디맨드는 "O(N) 덧셈화"라 적었는데 이미 O(N)이라 상한이 0.18ms였다. 성능 주장은 판정 전에 숫자를 뽑는다.
- `Length:Observer(fn)`은 생성 시 한 번 돌고 `:Subscribe()` 때 다시 돈다 — spec에서 emit 횟수를 셀 땐 구독 뒤에
  카운터를 0으로.
- luau CLI에서 spec 마지막에 절을 붙일 땐 `=== ALL PASS ===` 출력이 그 위에 있는지 볼 것 — 실패 assert의
  메시지가 안 찍히고 exit 1만 나오는 경우가 있었다(pcall 프로브로 격리해 찾음).

## 9. `/code-review` 반영 — `H-485`: 스왑이 `H-38`을 되돌리고 있었다

리뷰(단일 맥락, 서브에이전트 0)가 잡은 핵심: 오전에 적용한 `prevKeys = seen` 꼬리 교체는 `H-38`이 "마지막 일괄

뒤집힌 논거였다(선행 채움은 던지기 *전에* 집합에 들어가게 하려는 것, 꼬리 교체는 던지면 안 일어난다). RFC의
"수학적으로 동일"은 정상 경로에서만 참이다. 정정: 증분 기록 유지 + clone만 제거(`pairs` 순회 중 기존 키 삭제는
허용). 교훈 — **RFC의 등가 증명은 에러 경로까지 포함하는지 볼 것**, 그리고 옛 발견 번호(`H-38`)가 같은 자리에
붙어 있으면 그 계약 문장을 먼저 읽을 것. 나머지 다섯(열셋→열둘, quad-types 과장 주석, 동률 경고의 버킷 무시 +
게이트 순서, spec 26절 IndexOf 역맵 직접 단언, Clear 주석 수치)도 반영. 원장 §7.
