# 2026-09-02-04 — `H-305` (d′): D 타입 표면 → `UseProvider` 이원화 + fn identity 락

단위 ⑤의 `H-25` 확인에서 시작해 표면 설계 하나가 사용자 주도로 확정된
흐름. 발단·실측·확정 전량의 요약 원장은 round14 `H-305` 행(§4)이 소스 —
여기는 대화 경위와 인용 원문.

## 경위

1. **`H-25` 확인 중 `q.D` 타입 공백 발견** — `Quad`(엔진 무관)는 D 내용을
   못 싣고, `QuadRoblox<T>(quad: T): T`는 typing-limits §6상 타입을 못
   얹는다. §4에 `H-305`로 등재, 처음 권고는 (a) `D: any` + 생성 재익스포트.
2. **사용자가 `None: any` "선례"를 반박** — *"마커 필드가 생겼으면 any 일
   이유가 왜 있는거야?"* → 실측으로 확인: `H-300` 마커 이전 잔재(stale)가
   맞았고 `None: None`으로 좁힘(전 스위트 exit 0). (a)의 근거를 "선례"에서
   "자기 근거"(quad-types에 좁힐 타입이 존재 불가)로 정정.
3. **사용자가 AddPlugin 갈래를 제기** — *"차라리 D 형식을 plugin
   프로바이더로 넣는걸 고려해보고 싶어. 이것도 똑같은 문제가 있어?"*
   (spring 등 계획 정정 여부와 연동). 스파이크 실측(스크래치, 실 quad-types
   + D형 P + 체이닝 2회): `Self & P`는 테이블∩테이블(거주)이라 H10-3
   (함수∩테이블 무거주)과 계열이 다르고, **호출 인자 타입 검사까지 됨** —
   (a)를 엄격히 이기는 (d) 성립.
4. **사용자 회상으로 선례 재확인** — *"23 에서 플러그인 부분은 뭔가 더
   붙여나가는게 가능했었던거 같아서"* → `done/23`이 2026-08-19에 정확히
   이 모양(`checked:AddPlugin(installRobloxBackend)`)을 "quad-roblox가
   실제로 쓰게 될 패턴"으로 실측해뒀음을 확인. M5 단위 ①의
   `QuadRoblox(quad)` 직접 호출형이 오히려 그 스케치에서 이탈한 것이었다.
   깨졌던 건 체이닝이 아니라 별개 두 계열(type function 이력 오염 / H10-3
   무거주 교집합)이라는 정리도 이때.
5. **사용자가 (d)를 (d′)로 발전** — 셋:
   - mock 포함 **모든 프로바이더가 같은 형태**(*"프로바이더나 무엇이든
     전부 같은 형태를 가는거지"*).
   - **이름 분리** — *"오인 소지가 있어. 같은 동작을 하더라도 AddProvider
     형태로 가거나 해야하지 않을까?"* → Add는 복수 허용을 암시한다는 검토
     반영해 최종 **`UseProvider`**(*"UseProvider 쓰자 괜찮아 보여"*).
   - **fn identity 락** — 사용자 진단: *"지금 상황에서는 다른 곳에서
     로드된 두 quad-roblox(특히 버전이 다르다던가 등) 은 실패 없이 묵인
     처리 돼"*(실제 코드 확인: `_initializedBy == "roblox"` 문자열 비교가
     사본을 구분 못 함). *"한번 실행하면 해당 모델/함수의 identity 가지고
     락 거는 형태"* + 멱등의 실효성 근거도 사용자가 직접: *"require 을
     여러 곳에서 반복해도 같은 identity 의 Instance(ModuleScript) 라면
     캐싱으로 인해 같은 함수로 identity 가 같아서 실질적으로 일반적
     케이스는 성공해"*.
6. **확정** — *"확정하면 될것 같아"*.
