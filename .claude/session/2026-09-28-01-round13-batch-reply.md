이 세션부터 메인 모델이 fable 5.1에서 **opus 5.5(effort high)**로 바뀌었다. 사용자 근거: 앞 대화(rewind로 지움)에서 opus 5.5 서브에이전트에게 회신 단계용 시범 여섯 문항(원장 §0 해석, 가정 결정 아래 바뀌는 파일, 초안 자기모순, HEAD 대조 함정, 새 인자는 사용자 결정이라는 규약, assert-first 스크립트)을 줬더니 전부 정답이었고 fable이 놓친 것 둘을 잡았다. 규약의 뜻("반영·설계 대화에 능력을 낮추지 말 것")은 그대로이고 이름만 바뀐 것이라, `conventions.md`의 "fable 구간 임시 강하" 문단과 메모리 `feedback-model-choice-for-reflection`에 오늘 날짜 갱신을 달았다 — 큰 배치·낮은 난이도의 opus 서브에이전트 강하는 이제 메인과 같은 모델이라 의미가 없어졌고, 감사자 sonnet 고정은 그대로다. 사용자 단서 셋: (1) 벤치 비교는 xhigh 기준이라 high에선 보정이 필요하다 — **처음 묶음 몇 개는 감사 루프를 평소보다 한 라운드 더** 돈다. (2) 외부 리서치(`model-diff-ignoreme`, 커밋 제외)의 캐시 서술은 방향이 반대다 — 이 세션은 캐시 읽기가 지배하고 읽기 단가 격차가 가장 작으므로(0.20 대 0.25) 절감을 2.5배로 적지 않는다. 능력 하한을 effort로 표현하면 high(ARC-AGI-2에서 opus 5.5는 high가 최고). (3) **전환 사후 검증은 처음 묶음 다섯의 정정 커밋 수를 이 파일에 적는 것**으로 한다(아래 "사후 검증" 절). 같은 사이 사용자 커밋 `d5d25406`(errors/02 Quad0076 꼬리 힌트 다섯 정정 `H-866` + Q90 보강 ㉒ — 판정 재료 초안 `audit/round13-drafts-2026-09-27/q90-message-table.md`가 HEAD와 어긋난 셋)이 들어왔다 — Q90 반영 때 초안은 결정 재료로만 쓰고 문자열 앵커는 HEAD에서 다시 잡는다.

## 회신 기록

### Q90 — 메시지 모양 위반의 규칙 범위(2026-09-28)

메인이 결정 재료(자리·파일만으론 안 보이는 맥락·의견)를 정리하자 사용자가 되물었다: *"브랜드 없는 값이면 무조건 프로바이더로 떨어진다는게 무슨 의미임? 프로바이더가 설치된 환경에서는 무조건 properties 프로바이더가 캐치된 방향으로 나가아는거 아녔음?"* — 메인 설명: 프로퍼티 핸들러의 매치 조건은 "문자 키 ∧ `Parent` 아님 ∧ 그 클래스의 실제 프로퍼티"라 오타·읽기 전용·다른 클래스 이름·`Parent`는 거절되고, 받을 핸들러가 없으면 `Quad0076`의 힌트가 **키가 아니라 값의 브랜드만 보고** 프로바이더 안내로 떨어진다. 같은 턴에 사용자: *"하나에 여럿이 묶여서 읽기가 어렵네. 각 취향에 갈린다는 부분을 좀 더 서술해줄래? 의견인 b는 동의하긴 하는데, 번호로 붙어서 보기 어렵거든. 우선 에러의 메시지에 관한 다듬기로 보이는데, 그건 맞지?"* — 맞다(정상 경로 동작 불변, ID 불변).

`Quad0076`: 사용자 *"문자를 받는 키 핸들러가 있는지 보는건 매커니즘 추가 같고, 두개의 방식으로 에러가 날 수 있을 때 보통 그 두 경우를 알려주는데 그게 나을수도 있겠다는 생각. … 키 size 같은게 오타나 읽기 전용, 프로퍼티나 이벤트가 아니여서 없을 수 있다고 말 하거나, 아니면 quad-roblox 가 그걸 잡는 핸들러를 넣거나 이미 있는 방식을 재활용 하는게 나아보임"* → 메인이 두 갈래(중립 두 원인 문장 / quad-roblox 최하위 catch 핸들러 — 새 ID·서드파티 우선순위 제약·`H-148` 재개방)를 비교해 전자를 권했고, 사용자 *"나도 중립적으로 알려주는 안 동의"*. `H-148`(2026-08-28 `Parent` 전용 문구 철회 — 에이전트가 붙였던 새 메커니즘)을 메인이 이 대화 중에 찾아 알렸다.

취향 항목 여섯: 사용자 *"여기는 단어 선택이나 객관적으로 봐야할 부분이 많아서 sonnet 으로 선택에 대한 근거를 만들어 볼래? 외부자 내부자 시선으로 무엇이 나은지, 나처럼 주관적 시선이 아닌 객관적 시선에서 어떤지 보고싶음"* → sonnet 둘 병렬(외부자는 `.claude/` 금지). 결과: 둘 다 ③ 정규화·⑨ 유지; ②는 둘 다 대체로 유지(내부자는 규약 문장 추가 제안, 외부자는 Ref 둘 정규화 — 근거였던 "Callback 계열 메소드형 주어"가 HEAD와 달라 메인 정정); ④는 외부자 넷+Animate/Tween 예시 유지, 내부자 여섯 다(`H-477` 판례); ⑦은 외부자 문구 구체화, 내부자 유지; ⑧은 외부자 유지+규약, 내부자 재배치(원장이 놓친 `0176`·`0209`/`0211` 발견). 메인 종합(표) → 사용자 *"전체 종합 자체는 나도 동의해"*.

정적 자리 주어: 메인 권고 `Dispatch:` 통일에 사용자 *"dispatch 를 쓴다는 실제 코드에서 bookkeeping 네임스페이스가 있다는게 조금 걸리네"* — `0160`은 공개 op `q.Bookkeeping.claimOwnerAt` 안의 거부라 다른 이름을 대면 실제 자리와 어긋난다는 뜻으로 읽고, 메인이 "`0160`은 주어 유지 + 이유 절에 흔한 경로, `0219`/`0220`은 공개 이름이 없으니 `Dispatch:`"로 가르자 *"너가 말한 구분 동의해. 0160 만 dispatch 아니게 처리하는것도 옳아"*. `0138`: *"0138 는 지금 배치에서 빼고 천천히 정하자"*.

반영 내용·미룬 항목은 원장 §4 Q90 닫힘 문단이 소스. 메인이 스스로 정한 새 문구 셋(`0088`/`0090`·`0093`/`0115`·`0226`)은 커밋 전 사용자에게 보였고, 둘이 고쳐졌다. 사용자: *"'— a dead handle cannot be subscribed again; make a new Effect' 가 모든 effect 들이 한번만 사용될 수 있다고 읽히는데, 이건 threw 이후 불가하다 아니야?"* → "죽는다"의 주어를 던진 Effect로 좁힘(`… or after this Effect's fn or cleanup has thrown — a thrown Effect stays dead; create a new one`). 또 *"a weak sub... is released with ... 모양으로 두니 조금 모호한 느낌. strong 하지 않은 구독은 must be ... by 식이 되든 후행 문장만 읽을 때 오해가 없도록"* → 첫 절이 원인(`only a strongly subscribed Effect can be released with :Unsubscribe()`), 뒤 두 절이 각자 완결된 `must be released with/by …`. 감사 2라운드(1라운드 3건 반영 → 2라운드 확실 0건, 주석 1줄 정리).

**em-dash(부수 결정)**: 사용자 *"에러에 non ascii 인 — 가 있는건 괜찮을까 모르겠음. 보통 일반적으론 ascii 만 사용하니까. 이건 내 주관적 의견이라, 객관적 의견을 가지도록 sonnet 에이전트로 확인 해봐도 좋아"* → sonnet 판정: 전부 ASCII 권고(확신도 중간) — 관례 축이 강함(참고 Luau 라이브러리 다섯의 error 101건 중 non-ASCII 0), `error-id-plan.md`의 대괄호 기각(출력창 검색 편의) 전례, 표시 깨짐은 미실측 추정, 비용 작음; 구분자는 ` - `(콜론은 주어 구분자와 겹치고 `--`는 주석 기호, 괄호는 `(got X)` 전용). 메인이 "Q90 커밋 먼저, ASCII 전환은 별도 커밋"을 제안 → 사용자 *"그 순서로 가도 좋음. 구분자로 - 도 나쁘지 않고, 내가 생각했던 것임"*.
