## key 와 value 에 대한 바인드 연산은 pluggable 하도록 구성하기

[Event "name"] 같은건 결과가 테이블로 나와 테이블 키가 되며 = 뒤는 값
[1], [2] 등의 키에 대해서 = 뒤로 오는건 데이터가 됨

결과적으로 핸들러들은 key 와 value 를 받아보고 내가 받을 수 있는 데이터인가? 확인하는 ishandlable 정도를 구성함, 또한 우선순위를 설정 할 수 있게 두기
그것을 통해 여러 구조를 pluggable 하게 구성하면 될듯.

스토어 바인드는 특수 경우로 둘지, 아니면 다른 pluggable 바인드를 재실행하는 래핑으로 쓸지 생각해봐야함. 내 생각에 이것 또한 충분히 확장 가능하게 둘 수 있음.
그랬을 때 다만 slot 등이 스토어 바인드로 오는 경우 pluggable 바인드에 cleanup 핸들러 같은게 적당히 필요함. 또한 한번 넘어간 slot 에 대해서 나중에 cleanup 이 되면 삭제 되는건지. 부모의 소유이니 부모가 처리해야하는지 생각해볼 필요도 있음. 내 생각에는 부모가 clear 정도만 미리 수행하고 바인드 다시 하면 되니까, 부모에게 하라 해야할듯.

그리고 자식으로 넘기는 클래스 스토어는 위에서 생성하고 내리넘김 하는게 편할것 같긴함. 적절히 `store<<ChildClass.Props>>` 로 구성된 스토어를 만들면 된다고 생각함

레지스터의 실행은 내 생각엔 그냥 Destroy 되었는지를 라이프타임 홀더의 Connected 상태로 보는게 맞는듯.

## slot 을 구현하도록 하기로 했음

add remove clear get set 등의 뮤터블한 연산들을 지원하는 메타 배열로써 실제 바인드가 되면 child 로 풀리고 이 메타 배열에 대해 crud 연산을 하는 경우 적절하게 실제 children 이 제어될 수 있음. 단 이 slot 에 들어갔던 요소들은 ownership 이 귀속되며 다른 곳에 마운트 할 수 없게됨. 따라서 isMounted 를 적절히 관리하는 필요가 있음. 이전의 quad 는 mount 함수가 별다른 행동을 하지 않았지만. 이제는 mount 가 이런것을 다루도록 하여 한 인스턴스에 대한 다중 마운팅이 절대 일어나지 않도록 라이브러리 상에서 강제하는 디자인이 필요함

slot 은 하나의 instance 안에 여럿 존재할 수 있음. 모두 한 children 으로 들어가나, 실제 렌더링 된 instnace 에서 getchildren 을 한다던가 하지 않더라도 부모가 생성한 실제 slot 데이터 테이블을 다루기만 하면 되도록 하여 덜 직접적인 바인딩이 가능하도록 - 추상화가 가능하도록 함

클래스는 네이밍된(이 될 필요가 있나? 그냥 값으로 슬롯 바인드 테이블을 넘기는데. 그냥 스토어인데 array 처럼 구현되어있는거로 생각하는게 편하지 않음?) 슬롯을 받을 수 있는것으로 둠. (내 생각엔 스토어나 파라메터로 넘기고 그게 그냥 ref 처럼 바인드 되는게 맞는듯)

## store 는 부작용을 허용함. 그게 기본 디자인임.

물론 부작용이 없도록 구성하여 만들 수 있음, 파라메터로 받는 경우 그럼. 근데 원한다면 부작용을 허용하게 만드는것도 괜찮다고 생각함.
부작용 유무는 사용자가 문서화 하는걸로 두고자 함.

다만 옵저빙 하는걸 렌더 리턴 위에 두는건 그냥 부작용이 맞음. useEffect 랑 유사한 동작으로 문서화 하면 된다고 생각함.

## state 는 어떻게 구현하는가

만약 클래스 본인이 필요한 스테이트가 필요하면 그건 그냥 클래스 안에서 스토어 만들라 하면 됨. 내 생각에 store 는 부분 집합으로 패싱해서 보내는것도 충분히 가능하다고 생각해서, 하나에 넣어도 되지 않나란 생각이긴 해. 근데 원한다면 그냥 나눠도 좋고 그건 사용자 마음. 이걸 위해서 단일 store 인 state 를 제공할까 생각해봤는데, 굳이? 만약 구현 상 그게 더 편하게 된다면 state 를 만들긴 할텐데 아니라면 그냥 이전 처럼 할려고 하는중

테그 시스템이 있음. 물론 네임스페이싱 안 된다는 문제가 있긴 하지만 그건 나중에 생각해봐야할듯. 라이브러리로 격리 하는 경우는 필요할 듯 한데, 그렇게 필요한 부분인가 나는 잘 모르겠음 오히려 라이브러리의 복잡성을 너무 증가시킴

## 이제 클래스라는것은 특정 상태의 store 을 받는 함수임

훨씬 간단해짐. 글로벌 store 도 넣을 수 있고, 새로 생성된 store 도 넣어지고, 여러 방향에 있어서 확장적임.

따라서 글로벌에서는 slot 을 사용하는게 그닥 좋지 않을지도 모름.

## 시그널 자체 구현은 아닌듯

## 순수함수에 대한 범위를 정할 필요가 있음

컴포넌트는 순수해야하는가? 에 대해서 솔찍히 아직 모르겠음.
라이브러리화 할것이라면 순수한게 맞는데 만약 그냥 인게임 ui 라면 아닐수도 있고, 여러모로 생각해볼 거리가 많은듯. 다만 quad 는 기본적으로 순수함수에 대해서 필요성이 강조되지는 않지만, 디버깅이 꼬이는 문제가 분명 발생 중이기 때문에 확인이 필요함.

### 진짜 부작용은 외부에 만들어버린다

그냥 callback 등과 global store 의 값들을 관리하는 모듈을 만드는걸 관행으로 두는게 좋을수도. 거기에서 모든 부작용(리모트 함수 호출이나 리모트 함수로 부터 얻은 값의 바인드 등) 을 관리하면 사실 많은 부분이 해결됨

## 트윈은 어떻게 할것이냐

이건 처음부터 디자인이 잘못되었음. 렌더 라이브러리는 기본적으로 트윈을 직접 구현해서는 안 됨, 렌더링 엔진의 애니메이션 관리를 전혀 안 따르기 때문. 이 부분에 있어서는
[Tween (키, 트윈데이터...)] = 스토어값? 등
을 제공하는게 맞는듯. 처음 실행될 땐 그냥 바인드로 필드를 쓰지만 아닌 경우 스토어 값을 핸들 해서 바뀔 때 마다 처리해버리는거. 아니면 그냥 유저가 테그 얻던가 해서 관리하게 해.

## 스토어 값은 항상 먼저 캐치한다

당연함. 이걸 통해 cleanup 을 실행하는것도 가능하게 물론 해야지. 근데 트윈이 문제임. 그냥 이전 트윈 캔슬 하고 새로운 트윈 만들어서 실행되는게 맞긴 한데. 클린업 동작이 어떻게 될 지 정해줄 필요가 있을듯. 이거는 클린업 시 키 밸류를 먼저 얻게 해서 처리 가능하게 만들면 될것 같음. 키 밸류를 받으면 그로 인해 생성된 트윈을 얻고 멈춰버리거나, 아니면 키에 설정으로 트윈 뒤에 삭제 하지 말고 오버라이드를 할지, 삭제를 할지, 끝 지점으로 옮기고 새로운 트윈을 시작할 지 유저가 정할 수 있도록 둬야할듯. 그런 방식으로써 구현하면 문제 없지 않나 싶음.

## 네임스페이스드 객체

트윈을 하거나 할 필요가 있다 했는데. 이건 그냥 ref 를 사용하는걸 가정으로 두는게 맞는듯. 코루틴이 있으니 ref 가 채워질 때 까지 기다리는것도 가능하게 만들 순 있어 보이나 아직 이른듯. (문서화가 많이 필요한 부분이라)

네임스페이스를 제공하는건 생각은 해봤는데 솔찍히 성능적으로 별로 나쁜듯. 그냥 테그 서비스를 쓰는게 좋긴 할것 같은데. 그거와 별도로 있을 필요도 있나?

## 이미 생성된 객체에 대한 바인드?

이건 허용 안하는게 맞는것 같긴 함. 이미 생성된 객체에 또 새로운 {k=v} 를 바인드 가능하게 하면 이전 요소를 끊고 하는 작업이 필요할텐데, cleanup 이 구현되어 있다고 하더라도 바로 구현하는건 엔지니어링 비용이 높음.

## 넘버 바인드는 누가 처리?

좀 애매한 부분임. slot 이랑 잘 생각해서 구현해야함. 차라리 mount 가 처리하는게 맞는듯 한데 그러면 확장성이 있어질 수 있냐가 좀 문제임. 차라리 표준 구현체는 인터페이스만 놓고, 구현을 담는건 quad-roblox 정도 안에서 해당 인터페이스를 구현해야할듯. 그리고 런타임에 프로바이더로 roblox 를 받던가. 아니면 반대로 가던가 해야할텐데. 여긴 가상돔이 없어서 프로바이더로 roblox 를 받는 방식이 맞는듯 해보임.

## 모듈은 스코핑 되는가? (module.New 로 모듈을 만들 수 있냐)

애매한 부분임. 한 루아 스레드에서 두개 이상의 모듈 분화체를 쓸 일이 있냐 하면 보통 아님. 프로바이더를 로블록스와 비 로블록스를 동시에 한 루아에서 만들 일 있냐가 필요한가 모르겠음.
일단은 싱글톤으로 두고, 나중에 New 를 주는게 합당하면 주는걸 고려해야할듯.

## Quad 는 여전히 스크립트인가? 라이브러리인가?

이전엔 단순히 Instance 를 보조한다는 역할로써 스크립트로 분류했지만 지금은 확실히 라이브러리임. 구조화 되어있고 데이터타입이 존재함. 그냥 라이브러리로 두고 크게 구현하는게 맞는것 같음 기능에 대해서 별도로 묶는게 아니라 하나의 시스템으로 돌 수 있게, 그래서 위에서 나온 말이 pluggable 하게 두자는것임.
