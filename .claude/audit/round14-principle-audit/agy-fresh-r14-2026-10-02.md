### Q75 [E1, LOW] 배치·파동 중 native op에 stale offset 전달

1. **지금도 참인가: 여전히 참 [실측]**
   - **근거 코드**: [quad-base/src/Slot/Tree.luau:150](file:///code/Projects/quad-agy/fresh-r14/quad-base/src/Slot/Tree.luau#L150)
     ```luau
     local function unmountSlotTree(slot: any)
         if slot._mounted then
             module.Backend.nativeExtract(slot._mountedInst, slot.Offset:Get(), S.collectLeaves(slot))
         end
         teardownTree(slot)
     end
     ```
   - **확인**: `:List` reconcile이나 배치 Blocker 내부에서 Slot 트리 철거가 일어날 때, `slot.Offset:Get()`은 아직 상류/부모의 downstream recompute가 발생하기 전이므로 이전 세대의 오프셋(stale offset)을 그대로 읽어 `nativeExtract`에 넘긴다.
   - **다만 백엔드 영향 실측**:
     - `quad-roblox/src/EngineOps.luau:52`: `local function nativeExtract(target: any, _offset: number, elements: { any }, ...)` -> `_offset` 미사용.
     - `quad-base/test/mock.luau:463`: `local function nativeExtract(target: any, _offset: number, ...)` -> `_offset` 미사용.
     - 실제 Roblox 인스턴스 트리는 부모-자식 트리(`child.Parent = nil`)이므로 오프셋 정밀도가 물리적으로 불필요하다.

2. **바깥에서 보면 (외부 설계자 시각)**
   - UI 트리 렌더러에서 DOM/인스턴스 분리(unmount/extract) 작업 시 부모 노드와 자식 노드 간의 관계 해제는 인스턴스 참조 자체로 이루어진다.
   - 오프셋이 엄격하게 필요한 백엔드(예: 1차원 평면 배열 텍스트 버퍼)가 존재하지 않는 현재 상황에서, 배치 도중 매번 O(N) 비용을 들여 `getOffsetAt`을 재계산하는 것은 사용자의 대원칙("드문 오용이나 가상의 미래를 막으려고 구조를 늘리지 않는다")에 정면으로 위배된다.
   - **제안**: 계약을 "배치·파동 도중 native op에 넘어가는 offset은 트랜잭션 진행 중의 임시 참고값이며, 최종 정착 시점에만 논리 Offset과 일치한다"고 명시(갈래 (b))하고 코드는 그대로 두는 것이 가장 깔끔하다.

3. **문항 사이 연결**: Q125(List reconcile 성능), Q154(Slot 오프셋 테스트 공백)와 연결됨.

### Q97 [E10, LOW] 철거 retractor의 float/int 프로퍼티 등치 판정

1. **지금도 참인가: 여전히 참 [실측]**
   - **근거 코드**: [quad-roblox/src/Handlers/Property.luau:221](file:///code/Projects/quad-agy/fresh-r14/quad-roblox/src/Handlers/Property.luau#L221)
     ```luau
     tweenSlots:SetStrong(inst, k, if inst[k] == slot.Value then { Value = slot.Value } else true)
     ```
   - **확인**: 트윈 철거 시점에 프로퍼티에 실제로 쓰인 값(`inst[k]`)과 트윈의 목표값(`slot.Value`)을 strict equality(`==`)로 비교한다.
   - Roblox 엔진 내부에서 float32(예: `BackgroundTransparency`)나 정수(UDim offset)로 변환 저장되는 프로퍼티의 경우, Luau의 float64 값 0.1이 C++ 엔진에서 0.10000000149011612 등으로 반환되어 `inst[k] == slot.Value`가 `false`가 될 수 있다.
   - 결과적으로 슬롯 기록이 `{ Value = slot.Value }` 대신 `true`(target unknown)로 강등되어, 철거 후 완전히 같은 목표값으로 트윈을 재선언할 때 dedup되지 않고 보이지 않는 트윈이 1회 재시작될 수 있다 [추정].

2. **바깥에서 보면 (외부 설계자 시각)**
   - 만약 이를 해결하겠다고 `math.abs(a - b) < eps`나 UDim/Color3/Vector2 전용 비교기를 넣는다면, 디스패치 핸들러의 핫패스에 프로퍼티 타입별 분기문이 대량으로 추가되어 렌더러가 비대해진다.
   - 설령 `false`가 되어 `true`로 강등되더라도 발생하는 부작용은 "눈에 보이지 않는 동일 목표 트윈 1회 재생"뿐이며, 시각적 왜곡이나 크래시는 없다.
   - **제안**: C++ 엔진 저장 정밀도에 의존하는 엡실론 비교기를 도입하는 것은 과잉 엔지니어링이다. 현행 유지 후 문서화(갈래 (a))가 합리적이다.

3. **문항 사이 연결**: Q120(mock 충실도), Q157(엔진 프로퍼티 이벤트 특성)과 연결됨.

   - **확인**: 객체 팔이 `{ __apply: (self: any, state: any) -> any }`로 선언되어 있다. Luau에서 함수 매개변수는 **반공변(contravariant)**이므로, 사용자가 `state: State<number>`처럼 구체적인 타입을 주석으로 단 `__apply` 메소드는 `(any) -> any` 자리에 들어갈 수 없어 "None of the overloads"로 거부된다. 오직 `state: any`로 주석을 달아야만 통과한다.

2. **바깥에서 보면 (외부 설계자 시각)**
   - 함수형 팩토리 팔(`(State<T>) -> U`)은 제네릭 추론이 깔끔하게 동작하지만, 객체 팔은 `state: any`로 뭉개져 있어 오히려 사용자가 구체적 타입을 명시했을 때 컴파일 에러를 유발하는 역설이 발생했다.
   - 넘겨받는 `state`는 호출 리시버인 `State<T>`이므로 객체 팔을 `{ __apply: (self: any, state: State<T>) -> any }` 또는 제네릭 메소드로 선언하는 것이 자연스럽다.
   - **제안**: 우선 문서(`GS 13`)에 `state: any` 우회법을 명시하고, 가능하면 가급적 함수형 팩토리 사용을 권장하는 것으로 안내한다.

3. **문항 사이 연결**: Q145(`EffectFn` 타입), Q121(`Slot:Single` 타입)과 연결됨.

### Q145 [E56, LOW~MED] 두 갈래 Effect의 `return nil`을 타입이 거부함

   - **근거 코드**: [quad-types/src/init.luau:260](file:///code/Projects/quad-agy/fresh-r14/quad-types/src/init.luau#L260)
     ```luau
     export type EffectFn = (self: Effect) -> ...((dying: boolean) -> ())
     ```
   - **확인**: 가변 반환 `...((dying: boolean) -> ())` 표기로 인해, 한 갈래는 클린업 함수를 반환하고 다른 갈래는 `return nil` 또는 빈 `return`을 하는 분기 함수가 strict 모드에서 거부된다 (Luau가 반환 타입을 `T | nil`로 추론하는데 `...T` 팩에 매칭되지 않음).

2. **바깥에서 보면 (외부 설계자 시각)**
   - **본 과제에서 가장 명백하게 설계가 꼬인 지점 중 하나다.**
   - React의 `useEffect` 등 모든 리액티브 라이브러리에서 이펙트의 반환 시그니처는 `() -> (() -> () | nil)`이다.
   - Quad가 가변 팩 표기 `...T`를 쓴 유일한 이유는 "아무것도 반환하지 않는 함수(void)"를 허용하기 위함이었으나, 이 꼼수로 인해 가장 보편적인 `if cond then return cleanup else return nil end` 관용구가 차단되었다.

   - **제안**: 가변 팩 꼼수를 버리고 `export type EffectFn = (self: Effect) -> (((dying: boolean) -> ())?)`로 즉시 정상화(갈래 (a))하는 것이 압도적으로 우월하다.

     - ① 이종 Modifier 재태그: 237~242행에 "넷째 무검사 경로 — 클래스 생성자에 다른 클래스의 Modifier를 넘기기"로 완벽히 문서화 완료 [실측].
     - ③ `State<Ref>` 도달: 153행에 "UB(정의되지 않은 동작)"로 문서화 완료 [실측].
     - 잔여: ② Tag/Attr 값을 Modifier 필드에 넣을 때의 브랜드 거부 여부, ④ `Quad0123` 문구 개선.

2. **바깥에서 보면 (외부 설계자 시각)**
   - Modifier는 본질적으로 "속성 딕셔너리"다.
   - Tag와 Attr은 프로퍼티가 아니라 특수 디스패치 객체이므로, Modifier 필드에 잘못 들어갔을 때 마운트 시점에서 에러가 나는 것은 지극히 자연스럽다. 굳이 Modifier 생성 시점에 O(K) 검사를 추가할 이유가 없다.
   - 반면 ④ `Quad0123`("Apply target must be a State") 에러 문구가 `:Apply`를 가리켜 개발자가 원인을 찾기 어렵다는 점은 순수한 DX 결함이다.
   - **제안**: ②는 마운트 시점 에러로 두고, ④의 에러 메시지만 더 친절하게 다듬는 것(polish)으로 마무리하는 것이 이상적이다.

3. **문항 사이 연결**: Q117(에러 ID 및 문구 개선), Q144(`Apply` 타입)와 연결됨.

### 3.2 "바깥 시각에서 가장 다르게 보이는 셋"

외부 라이브러리 설계자의 객관적인 눈으로 보았을 때, 내부의 복잡한 논의/감사 루프와 가장 큰 시각 차이를 드러내는 3가지는 다음과 같다:

#### 1. Q145 & Q144 — 타입 시스템의 과잉 꼼수 vs 표준 관용구의 충돌
- **내부 논의**: "이펙트 클린업 함수가 없는 경우(void)"를 타입으로 표현하겠다고 가변 반환 `...((dying: boolean) -> ())`이라는 기괴한 Luau 팩 표기를 도입했다.
- **바깥의 시각**: 이 꼼수 때문에 함수형 프로그래밍과 React 생태계의 가장 자연스러운 관용구인 `if cond then return cleanup else return nil end`가 컴파일 에러를 뱉는 치명적인 DX 저하가 발생했다. Luau에서 `() -> (((dying: boolean) -> ())?)` (옵셔널 반환) 하나면 클린업 반환, nil 반환, 반환문 생략이 모두 우아하게 지원된다. 타입체커 내부 트릭에 집착하다가 사용자 대면 사용성을 훼손한 전형적 사례다.

#### 2. Q140 & Q75 & Q139 — 실패·파괴·과도기 상태의 "완벽한 일관성"이라는 허상
- **내부 논의**: 엔진 `setAttr` 실패 후 소유권 잠김(Q140), 배치 도중의 stale offset(Q75), 파괴 중 조상 Observer 발화(Q139) 등을 두고, 트랜잭션이 실패하거나 파괴되는 과도기 상태에서도 내부 상태가 완벽히 일관성을 유지해야 하는지에 대해 장시간 고민하고 있다.
- **바깥의 시각**: 사용자의 대원칙("던진 뒤 라이브러리 상태 무결은 비약속", "파괴 중 상류 되먹임은 UB")에 이미 명확한 답이 나와 있다. 실패한 트랜잭션의 롤백이나 파괴(cleanup) 단계에서의 역방향 상태 전파는 **본질적으로 정의되지 않은 동작(UB)**이다. 여기에 트랜잭션 원자성이나 동기적 완벽성을 부여하려는 시도는 라이브러리를 거대하고 무거운 괴물로 만드는 지름길이다.

#### 3. Q120 & Q97 — 단위 테스트 Mock과 실제 엔진 시뮬레이터의 혼동
- **내부 논의**: mock을 실제 Roblox 엔진의 비동기 Deferred 큐, 동기화 특성, 태스크 격리까지 100% 동일하게 에뮬레이트하려 하거나, C++ 엔진의 float32 저장 정밀도 오차(0.1 -> 0.10000000149)를 극복하기 위해 디스패치 핸들러에 온갖 타입별 엡실론 비교기를 넣으려 한다.
- **바깥의 시각**: mock 백엔드는 Quad 자체의 리액티브 그래프와 부기 로직을 검증하기 위한 **빠르고 결정론적인 단위 테스트 도구**일 뿐이다. 엔진의 C++ 내부 구현 특성이나 렌더러 정밀도 한계를 프레임워크 핸들러나 mock에 끌고 들어오는 것은 심각한 과잉 엔지니어링이며, 엔진 특화 동작은 실기기 통합 테스트(`HUMAN_TODO`)로 분리하는 것이 건강한 소프트웨어 공학의 기본이다.
