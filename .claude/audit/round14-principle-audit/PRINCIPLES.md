# round14 원칙 감사 — 판정 기준 (2026-10-01)

사용자 지시(`session/2026-09-28-01-round13-batch-reply.md` 2026-10-01 끝 절들): *"전반 경향을 볼 때 code-review 나 다른 입력을 유저 입력처럼 받아 구현되어 문제 생긴게 많은것 같은데 … 프로젝트 전체 규모에 있어서 비슷하게 원칙을 어겼거나 한게 없는지 확인을 해야할 것 같아"*, *"한번 프로젝트 전체에 원칙 문제를 보고 시작하자. 뭔가 더 꼬이면 풀기 힘들어지겠어."* 아래는 감사자와 round14 재검토가 같은 잣대를 쓰도록 모은 원칙 목록이다 — 출처는 각 줄의 문서가 정본이고, 이 파일은 색인이다.

## A. 결정의 출처

- **A1. 새 필드·인자·이름·메커니즘은 사용자 결정이다**(`conventions.md`의 "`/code-review`(그리고 메인 세션 자신)가 내놓는" 항목, 2026-08-27). 리뷰·탐사·자율 ① 반영(`H-nnn`)이 이런 것을 들였다면 사용자 원문이 있는지 확인한다. 증상만 확실하고 처방이 새 개념이면 "증상 확정, 처방 미정"이어야 했다.
- **A2. 사용자 인용문 옆에 새 메커니즘을 붙이지 않는다** — 인용이 승인한 것과 그 옆의 리뷰 제안을 갈라 적었는가.
- **A3. 이전 결정과 대조했는가** — 같은 모양이 과거에 기각·UB로 정해진 적이 있는데 그걸 인용하지 않고 반대로 만든 곳(2026-10-01 회고에서 Q111·Q76·round1 Q4·`H-101`이 이 사고였다).

## B. 구조 원칙

- **B1. 드문 오용이나 가상의 미래 요구까지 방어하려고 구조를 복잡하게 만들지 않는다**(`conventions.md` "설계 원칙" 첫 항목) — 실제로 관측된 문제에만 구조를 쓴다. 단 입구 한 줄 검사처럼 비용이 압도적으로 싼 품질 개선은 예외(2026-09-30 보정).
- **B2. 하나가 두 일을 하지 않는다 / 이질적 타입끼리 본문을 공유하지 않는다**(같은 절 둘째 항목).
- **B3. Dispatch는 코어 객체를 알지 않는다 — 각 객체를 아는 곳은 그 객체가 선언된 곳**(`H-278`, `architecture.md`; 2026-10-01 None·StoreBind·BRAND_PROBES 정리).

## C. 반응형 계약(2026-10-01 확정 — 정본 레퍼런스 `docs/reference/core/05-observer-effect.md` "Observer는 최종 소비자" 문단, 경위 `base/source-state-plan.md` "Compute 순수성" 절)

- **C1.** 반응형 콜백은 파동 도중 yield하지 않는다(모든 콜백에서 UB). 꼬인 파동을 풀어 주는 도구가 없는 곳에서 자기 입력을 되먹이지 않는다.
- **C2.** Compute는 어떤 State도 Set하지 않는다(UB). Compute 안 yield·재진입도 UB.
- **C3.** Observer는 최종 소비자 — 다른 대상 Set은 정상, 자기 상류 직·간접 되먹임은 UB. 예외(정의된 경로): `q.Out`/`OnChange` 엔진 왕복, Slot `Offset`/`Length` CRUD 고리(부기 되감기가 수렴시킴).
- **C4.** Effect의 자기 의존성 Set만 지연 재실행으로 정의됨; 한 루프 1만 회 넘으면 `Quad0263`.
- **C5.** `Source:Set`은 같은 값도 늘 전파(`H-68`), `:Emit`은 값 그대로 전파, 비교 쓰기는 명시적 `:SetIfChanged`.
- **C6.** UB 입력 안의 동작을 다듬는 가드·메커니즘은 쌓지 않는다 — 2026-10-01 회고가 걷어낸 것(`archive/ub-mitigation-loops-and-guards-withdrawn.md`)과 같은 결의 것이 남았는지.

## D. 계약·문서

- **D1. UB 결과를 spec·문서 계약으로 고정하지 않는다** — 남길 땐 "관측 — 계약 아님" 표시.
- **D2. 예외 안전성 — 사용자 콜백을 pcall로 감싸지 않는다, 던진 뒤의 부기 무결은 약속하지 않는다**(`architecture.md`의 "예외 안전성 계약", round3 Q18 (c) *"에러로 죽은 다음 우린 데이터의 무결이 깨져도 상관이 없고"*).
- **D3. 에러 메시지는 API가 아니다**(공개 표면 (11)).

## E. 검사의 층(`architecture.md`의 "debug 층" 절)

- **E1.** 설계에 들어가기 전 입구에서 잡히는 "받지 않는 값"은 에러로 알려 준다(입구 한 줄 검사는 평소 경로에 둔다).
- **E2.** 비싸거나 깊은 검사(조상 사슬 걷기, 전수 스캔, 핫 패스의 브랜드 스캔 등)는 `q.debug` 층. debug 검사 본문은 파일 위쪽 함수로, 로직엔 한 줄.
- **E3.** 핫 패스(매 emit·매 drive·매 Set)에 상시 가드를 두지 않는다.

## 판정 갈래(감사자가 각 메커니즘에 붙일 것)

- **(가) 원칙 위반·사용자 결정 없음** — 걷어낼 후보(무엇을 지우면 무엇이 바뀌는지, 어느 spec이 그 동작을 고정하는지).
- **(나) 사용자 결정은 있으나 근거가 이후 결정으로 사라짐** — 재검토 후보.
- **(다) 층이 틀림** — debug로 내리거나(E2·E3) 반대로 입구로 올릴(E1) 후보.
- **(라) 문제없음** — 개수만.
