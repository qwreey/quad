# Naming review — two new methods on a reactive UI library's module object (quad, Luau/Roblox)

You are reviewing public API names. Judge them from the point of view of the library's USERS — people who write component kits and games on it. Everything you need is below — do not look for files. Reply in Korean, concisely: for each item your pick, a ranked shortlist (you may add one candidate of your own), one or two reasons; flag any name that would mislead.

## Context
- quad is a reactive UI library. A game gets the library's module object `q` once, in its own setup module: `local q = Quad:UseProvider(QuadRoblox)` — `UseProvider` installs a backend ("provider") that adds the Roblox surface (`q.Elem "Frame"`, `q.Tween`, …). Existing methods on `q` (PascalCase, colon call): `q:UseProvider(providerFn)` (install the backend; the same provider again is a no-op, a different one errors), `q:AddPlugin(pluginFn)` (merge extra fields into q), `q:RunInit(initFn)` (run initFn once per q — no return value), `Quad.NewModule()` (a fresh independent q), field `q.Version` ("3.4.0"). Elsewhere the library already has `q.Context` with `Context.Provider` (a value provider — different meaning of "provider"). Internally the library uses `_assertXxx` private hooks that throw when a precondition fails.

## Names to judge
1. **Per-q result cache.** `q:X(key, build)` — the first call for a key runs `build(q)` and stores the result inside q (strong key, strong value — gone with q); later calls with the same key return that same result without running build. The key is any value: a kit module passes its own build function (`return function(q) return q:X(build, build) end` or shorter `q:X(build)` when the key is the function itself), a kit root passes a string like `"quad_kit_roblox_devui_7"` so two installed copies of the same kit share one result. Calling X for a key whose build is still running (a cycle) errors. Difference from `RunInit`: RunInit only runs once; X returns the cached value. Candidates: `Memo`, `Once`, `Cached`, `Shared`, `GetOrCreate`, `Singleton`, `Lazy`.
   Also: should the key be a separate first argument always (`q:X(key, build)`), or optional (`q:X(build)` keys by the function, `q:X(build, key)` with an explicit key)? Pick one shape.
2. **Assert the backend is installed.** `q:Y(name, versionPattern)` — throws (with a message telling the user to call `UseProvider` in the game's setup module first) unless q has a provider that declared that name and a version matching the pattern; returns nothing (or q). A kit root calls it once: `q:Y("quad-roblox", "3.4^")`. It compares by declared name + version, not by function identity, because the kit's copy of the provider package may be a different copy than the game installed. The user prefers an `Assert…` name (it errors, like Lua's `assert`, and matches the library's private `_assert…` hooks). Candidates: `AssertProvider`, `AssertBackend`, `AssertProvided`, `AssertUsing`, `AssertProviderVersion`.
3. **How the provider declares its name and version** (needed by 2) — just the field/term names: candidates `Name` / `Version` on the extension table the provider returns, `ProviderName` / `ProviderVersion`, or a single `Provider = { Name, Version }` entry. Pick the clearest; the library's own version is already `q.Version`, so note any clash.
