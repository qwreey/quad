# `updateFn` 인자 테이블 — 새로 만들기 vs 재사용 실측 (2026-09-15)

**발단**: `research/public-surface-pre-adoption-review.md` (7)번. 사용자: 인자를 테이블로 넘기되 한 테이블을 재사용하고 패스 뒤 `table.clear`하면 비용이 거의 0이라는 제안 → 메인이 클로저 캡처 위험(React 16 이벤트 풀링 선례)을 짚자 사용자: *"t.clear 와 그냥 계속 생성하는 테이블 간 성능 편차를 실즉하고, 별다른 문제가 없다면 후자로 단순 생성하는게 나아보여 … 최적화 래벨 따라 얼마나 달라질지도"*.

**환경**: luau CLI 0.734(mise), Linux, 중앙값 5회. 스크립트 둘이 이 폴더에 있다.

## 1. 마이크로 — 호출 2,000,000회(1000항목 × 2000패스), `updateFn`은 필드 다섯을 읽기만

| 방식 | -O0 | -O1 | -O2 | -O2 --codegen |
|---|---|---|---|---|
| 위치 인자(지금) | 26.2 ns | 25.1 ns | 16.8 ns | 8.7 ns |
| 새 테이블 매 호출 | 97.6 ns | 76.0 ns | 68.3 ns | 55.4 ns |
| 재사용(필드 덮어쓰기) | 48.0 ns | 47.5 ns | 37.8 ns | 28.6 ns |
| 재사용 + 매 호출 `table.clear` | 101.8 ns | 92.0 ns | 81.0 ns | 83.4 ns |
| 재사용 + 패스마다 `table.clear` | 47.9 ns | 47.4 ns | 38.9 ns | 29.2 ns |

- 새 테이블은 재사용보다 호출당 **약 27~50 ns** 더 든다(최적화 레벨이 올라가도 차이의 절대량은 크게 안 준다 — 할당·GC가 지배).
- **매 호출 `clear`(오용을 바로 드러내려는 형태)는 새 테이블보다도 느리다** — 재사용이 싼 건 "패스 동안 이전 항목 값이 남아 있는" 형태뿐이다.

## 2. 실제 reconcile(mock 백엔드) — 1000항목 갱신 패스 30회, 모든 키 유지·`prev` 반환(가장 가벼운 `updateFn` = 최악 비율)

| 방식 | -O0 | -O2 | -O2 --codegen |
|---|---|---|---|
| 위치 인자 | 23.9 ms | 18.1 ms | 14.6 ms |
| 새 테이블 | 30.1 ms | 21.9 ms | 18.9 ms |
| 재사용 | 25.6 ms | 19.4 ms | 15.8 ms |

1000항목 한 패스당: 새 테이블 +0.13~0.2 ms, 재사용 +0.04~0.06 ms. **새 테이블 − 재사용 ≈ 패스당 0.1~0.15 ms**(1000항목).

## 해석

- 차이는 `updateFn`이 **아무 일도 안 할 때**의 비율이다. 실제 `updateFn`은 인스턴스·`:Compute` 노드를 만들고, Roblox 백엔드의 `native*`는 mock보다 훨씬 비싸서 실사용 비율은 이보다 작다(실기기 미측정).
- 1000항목 리스트를 **매 프레임** 전부 갱신해도 새 테이블의 추가분은 16.6 ms 프레임의 1% 안팎.
- 재사용의 이득(패스당 ~0.1 ms/1000항목)은 클로저 캡처 시 조용히 틀린 값을 읽는 약점, 그리고 그걸 에러로 드러내는 가드(매 호출 clear는 오히려 느림, `__index` 가드는 추가 비용·복잡도)와 맞바꿀 규모가 아니다.
- **결론(메인)**: 사용자 조건("별다른 문제가 없다면 후자") 충족 — 매 호출 새 테이블.
