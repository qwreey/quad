# devui 팝업 모델 — 붙어 여는 팝업, 가운데 여는 대화상자, 막는 범위 (계획서, 결정 아님)

**[2026-10-21 신설]** devplorer 상향 보고서 2차(`feedback/devplorer-2026-10-21.md`)의 팝업 묶음(1차 묶음 다: 팝업 몸통 공개, 화면 안 고정, 임의 좌표 메뉴, 분할·메뉴 단추, 메뉴 유지)을 정하다가 사용자가 한 층 위의 모델을 꺼냈다. 이 문서가 그 모델의 계획서다. 상태의 소스는 맨 끝 "결정 기록" 절.

## 1. 계기 — 사용자 발언

메인이 "모든 팝업이 화면 안으로 밀려 들어오는 것을 기본 동작으로"를 권하자 사용자:

> *"팝업이 화면 안에 머물기는 여타 다른 wayland 컴포지터와 유사하게 가능할것 같네. 팝업 안이 더 크면 문제가 되니까. 창 밖에 렌더되어야하는것 같고. 일반 팝업과 똑같은데 중앙에 열리냐 아니면 그 창에 인접하게 열리냐가 중요한듯. 그런데 다른것도 봤어. 중간에 열리는것 중에 다른 액션을 차단해야하는 중요한건 toplevel 로 놓이는것도 필요가 보이는듯. 삭제나 그런것을 위해서? 그리고 팝업은 내 생각엔 다른 창보다 항상 최상위이고 toplevel 과 차이는 배경을 dim 하는 범위 차이인듯. 연 창을 dim 하냐, 아니면 그냥 따로 보고 dim 아무것도 안하냐, 글로벌 하게 dim 해서 입력을 빼앗냐 차이? 특히 삭제 이런건 다이어로그 도중 유저가 창 안에 다른걸 만지면 안되니까 필요하지 않나 싶음(입력을 빼앗는 오버레이로)"*

같은 회신에서 닫힌 것: 분할 단추와 메뉴 단추를 위젯 하나로(`OnClick`이 있으면 분할, 없으면 단추 전체가 메뉴), 메뉴 유지 옵션(가칭 `KeepOpen`), 팝업 몸통 공개(가칭 `PopupPanel`). 이름은 세 모델 검토 뒤(사용자 지시 — `audit/naming-devui-2026-10-21/`의 방식).

## 2. 지금 상태 [2026-10-21 기준]

- 모든 팝업은 `Overlay` 층(ZIndex 1000, 창들 위)에 그려진다 — "창 밖에 렌더"는 이미 그렇다. 창 관리자가 창 순위를 Overlay 아래로 지킨다(`Window/Manager.luau` 머리, 333창).
- 배치는 여는 쪽 몫이다(`Overlay.luau` 머리 "Positioning": 화면 안 고정은 내용 크기가 필요하니 여는 쪽이 하라). 그래서 제각각이다: devui `Combo`는 2026-10-21부터 아래가 모자라면 위로 뒤집고 남은 공간까지 줄인다, devui `Menu`는 항상 앵커 아래/오른쪽, `Tooltip`은 마우스 옆 그대로, material `Menu`는 뒤집기 + 가로 당기기, devplorer는 같은 당기기 코드를 세 곳에.
- 막는 범위는 둘뿐이다: 바깥 클릭으로 닫히는 팝업(화면 전체 투명 막 `Catcher` — 입력은 빼앗지만 어둡게 하지 않음, 누르면 닫힘)과 막 없는 팝업(툴팁). "닫히지 않고 입력을 막는" 대화상자는 devui에 없다. material `Dialog`에는 화면 전체 scrim(어둡게 + 입력 막기)이 있다.
- 창 하나만 덮는 장치는 이미 하나 있다: 분할의 작은 쪽 덮개 `WindowDim`(창 표면 루트 안, 누름을 먹음 — 2026-10-21).

## 3. 제안 모델

### 3.1 배치 — 붙어 열기와 가운데 열기 (Wayland `xdg_positioner`와 같은 생각)

팝업은 **앵커 사각형**과 함께 연다. 메뉴 막대 항목·Combo 상자·분할 단추는 그 요소의 사각형, 우클릭 메뉴는 크기 0인 포인터 점이다. 앵커의 어느 변에 붙고 어느 쪽으로 자라는지(아래로·오른쪽으로 등)를 정하면, 내용 크기가 정해진 뒤 Overlay가 화면(층) 안에 들도록 **차례로** 맞춘다.

- **뒤집기**: 그 방향에 자리가 모자라면 반대쪽으로(아래 → 위, 오른쪽 → 왼쪽).
- **밀기**: 그래도 넘치면 가로·세로로 밀어 넣는다(앵커와 겹칠 수 있음).
- **줄이기**: 내용이 층보다 크면 층 크기로 줄이고 스크롤한다(사용자: *"팝업 안이 더 크면 문제가 되니까"*). 스크롤을 줄 수 있는 내용(목록·메뉴)만 — 그렇지 않은 내용은 밀기까지만.

가운데 열기는 같은 장치의 다른 앵커다: 앵커 = **층 전체**(화면 가운데) 또는 **여는 창의 사각형**(그 창 가운데). 사용자 말대로 "일반 팝업과 똑같은데 중앙에 열리냐 인접하게 열리냐"의 차이라, 배치 규칙은 하나다.

메인 권고: 이 배치를 `Overlay:Open`의 기본 동작으로 넣는다(앵커를 안 주면 지금처럼 점 하나 = 그 자리). 기존 호출(Menu·Combo·Tooltip)은 앵커를 넘기도록 바꾸고, Combo의 자체 뒤집기는 이리로 옮긴다.

### 3.2 막는 범위 — 셋

사용자 정리 그대로, 팝업과 대화상자(toplevel)의 차이는 **어둡게 하고 입력을 막는 범위**다. 셋으로 둔다.

- **없음**: 아무것도 어둡게 하지 않고 막지 않는다. 툴팁, 그리고 열어 둔 채 다른 일을 하는 대화상자(찾기 상자 같은 것).
- **여는 창**: 그 창만 어둡게 하고 그 창의 입력을 막는다. 다른 창은 쓸 수 있다. 창 하나에 묶인 확인(그 창의 항목 삭제). 장치는 이미 있는 `WindowDim`과 같은 꼴 — 창 표면 루트 안의 덮개라 창이 움직이거나 붙거나 탭으로 묶여도 따라간다.
- **전체**: 층 전체를 어둡게 하고 모든 입력을 막는다(material `Dialog`의 scrim). 되돌릴 수 없는 일(사용자 예: 삭제)이나 앱 전체가 답을 기다려야 할 때.

메뉴·Combo처럼 **바깥을 누르면 닫히는** 팝업은 막는 범위와 별개 축이다(지금의 `Catcher` — 어둡게 하지 않고, 누르면 닫힘). 대화상자는 바깥을 눌러도 닫히지 않는다(답을 받아야 하므로) — 막는 범위가 "여는 창"이면 그 창의 덮개가, "전체"면 층의 덮개가 누름을 먹는다.

메인 의견: 사용자 예(삭제)는 **여는 창**으로 충분한 경우가 많다 — 사용자가 걱정한 것은 *"다이어로그 도중 유저가 창 안에 다른걸 만지면"*이고, 여는 창 막기가 정확히 그것을 막는다. 다만 무엇이 지워지는지가 다른 창에서도 바뀔 수 있으면(같은 데이터를 두 창이 보여 줌) 전체가 맞다. 그래서 대화상자가 범위를 고르게 하고, 기본값은 "여는 창"을 권한다.

### 3.3 대화상자 부품

- 가운데(층 또는 여는 창)에 여는 `PopupPanel` + 제목 + 단추 줄. 끌어 옮기기는 처음엔 없음(필요하면 창으로 만들면 된다 — 창은 이미 끌림·도킹이 있다).
- Escape: 취소 단추가 있으면 그것과 같게. 포커스는 대화상자의 첫 단추.
- 확인 도우미(material `Dialog.confirm`과 같은 자리) — 삭제 확인 한 줄로.
- devplorer의 `Popups.Confirm`(후보 목록 6번)·`CopyDialog`(7번)가 이 위에 선다.

### 3.4 메뉴 선언 — 1차 질문 (가)/(나)의 자리

임의 좌표 메뉴는 3.1의 "포인터 점에 붙어 여는 팝업"이다. 메뉴를 **선언하는 법**((가) 지금의 `Children = function(scope)` 팩토리 + `MenuItem`들, (나) 표로 넘기는 선언형)은 배치·막기 모델과 **따로** 정해진다 — 어느 쪽이든 3.1의 앵커 = 포인터 점으로 연다. 메인 권고는 그대로 (가)(메뉴를 만드는 법이 하나, `Hooks`·토글·하위 메뉴·`Separator`가 다 됨).

## 4. 순서 (권고)

1. 배치(3.1)를 Overlay 기본 동작으로 — 이름이 거의 없는 일(앵커 인자 모양만). 메뉴·Combo·툴팁이 바로 덕을 본다.
2. 팝업 몸통 공개 + 임의 좌표 메뉴 + 분할/메뉴 단추 + 메뉴 유지 — 이름 넷을 세 모델 검토로.
3. 막는 범위(3.2)와 대화상자(3.3) — 이름(대화상자 부품, 범위 값)을 세 모델 검토로.

## 5. 정할 것

1. 배치 규칙: 뒤집기 → 밀기 → 줄이기(스크롤 되는 내용만) 순서, 그리고 Overlay 기본 동작으로 넣기.
2. 막는 범위 셋(없음·여는 창·전체)과 대화상자의 기본값(권고: 여는 창).
3. 대화상자는 끌어 옮기지 않음(처음엔).
4. 메뉴 선언은 (가) 그대로.
5. 순서(4절).
